# port-net-predict — Known Limitations

- **Campaign co-op: scripted single-target object gives reach the wrong player on the client (e.g. Cassandra's necklace, `setupame.c`).** The necklace is handed out by a *script* (`aiGiveObjectToChr` → `CHR_COOP`), not a proximity pickup. `CHR_BOND`/`CHR_COOP` map to **different physical players on each machine** — on the client the local player is always slot 0 (`netPlayersAllocate` swap) and the host occupies the "coop" slot — so the host gives it to its `CHR_COOP` (= the client, correct, which is why the **objective still completes host-authoritatively and the "Objective Complete" toast shows**), but on the client the same script targets `CHR_COOP` = the *remote host*, so the **local player never gets the item in its own inventory** and the bottom-left "picked up X" toast never fires.
  - **Not mission-blocking:** the gate that the item unlocks (e.g. the basement door) is host-driven — when the host's `CHR_COOP` has the necklace the script sets the stage flag, which is mirrored to the client (`SVC_STAGE_FLAGS`), so the door opens for everyone. Only the client-side inventory entry + pickup toast are missing.
  - **Attempted fixes that don't work** (see `PORT_NET_REVERTED_EXPERIMENTS.md` if expanded): (1) client skips *all* scripted player-gives and relies on the host's `SVC_PROP_PICKUP` — **breaks the spawn loadout**, because spawn gives run before the client is reliably in `CLSTATE_GAME` so the broadcast is dropped (the local give has no such timing dependency); (2) apply the host's echo for non-proximity gives via a syncid-tracked skip-own filter — the necklace lands correctly but the **spawn loadout doubles** (local give + SVC echo), corrupting the ammo counts the mission's "mines wasted" checks read.
  - **FIXED ("option 3", compile-verified, needs a runtime co-op pass):** on the *client*, `aiGiveObjectToChr` now remaps any resolved `PROPTYPE_PLAYER` target back through the `netPlayersAllocate` slot-0 transposition (`netCoopRemapWirePlayernum`, net.c — exposes the `s_netSlot0SwapOccupant` swap as a self-inverse wire-slot <-> local-slot map). The script-resolved LOCAL slot is exactly the wire slot the host targets (both machines resolve `CHR_BOND`/`CHR_COOP` via `bondplayernum`/`coopplayernum` = 0/1), so transposing it back lands every scripted give on the same **physical** player as the host: single-target gives (necklace) reach the local inventory + toast, and multi-target gives (spawn loadout) still run exactly once per pawn — no SVC echo involved, and the host's `SVC_PROP_PICKUP` echo for the client's own pawn is already skipped in `netmsgSvcPropPickupRead`, so nothing doubles. Identity map on the server, on no-swap clients (first joiner), and for drop-in claimants (seated at their wire slot). Regression watchlist for the runtime pass: spawn loadout counts (Air Base "mines wasted" check), necklace inventory + toast on the client, and a 3-4-player drop-in session.

- **Slayer fly-by-wire on clients — IMPLEMENTED (proto 76), compile-verified, NOT yet runtime-tested.** Server-authoritative flight + wire-carried steering + client-local camera: the firing client engages the rocket-cam on its synced rocket and sends per-tick rotation rates (`UCMD_FLYBYWIRE` + the `fbw_pitch/yaw/rsticky` move tail); the server's steering branch (`playerTick`, `fbw_srv_remote`) flies the authoritative rocket from those rates and streams pos/rot back via the existing SVC_PROP_MOVE path. Accepted caveats: camera/steering response lags ~RTT (inherent to server-authoritative flight); camera orientation steps at the svcrate (30 Hz at `--svcrate 2`); spectating a flyer shows a frozen first-person (the observer's pawn never engages the vision mode). Needs a coordinated proto-76 deploy (VPS + all clients). See the `whimsical-booping-raccoon` plan; FarSight alt-fire still doesn't work on clients.
- **Dropped-item physics (ammo boxes / dropped guns) no longer run on some machines** (user-reported 2026-06-10, regression window = the WIP projectile-sync work in 58fed026e and after). Dropped items fall via `OBJHFLAG_PROJECTILE` physics through the same `projectileTick` that rockets use, so they're subject to the `objTickPlayer` fulltick gates (propobj.c ~11250-11286): the owner gate only fullticks player-owned projectiles on the owner's `propsTickPlayer` iteration, and the client-side fly override requires `prop->syncid` + the primary-local-pawn iteration. A dropped crate that doesn't qualify under any gate (e.g. owner is a remote/disconnected player's pawn, or a client-local syncid-0 drop) freezes mid-air instead of falling. **2026-06-11: symptom MASKED for synced props by the Combat Sim dynamic-prop position stream** (net.c `netEndFrame`, catalog §5.2 fix — a never-ticked client copy still follows the wire to the floor; pass-2 heals settled divergence). Client-local syncid-0 drops have no wire stream and can still freeze; root the gates when the projectile-sync WIP resumes (`net-projectile-sync` memory has the gate map).
- **Sim-dropped hand weapons exist as TWO parallel copies** (long-standing — predates
  port-net-predict; root-caused 2026-06-11 during the projectile-sync hunt; NO visible
  bug in play, user-confirmed). A sim's hand weapon is given server-side via
  `chrGiveWeapon` (dynamic syncid, never spawn-broadcast — while held it's parented so
  nothing wire-references it); the client mirrors the hands with its own LOCAL syncid-0
  props (the chr-state weapons-held sync). When the sim dies, BOTH machines put their
  own copy on the floor: the server's (authoritative, syncid'd — and now in the §5.2
  per-tick move stream, which is what produces the throttled client warnings
  `prop with syncid N does not exist` / `obj body for syncid N unapplied — consumed`)
  and the client's local visual twin. Pickups are server-granted by proximity so play
  works; the costs are per-tick ghost-move bandwidth for every gun on the floor,
  possible visual-vs-authoritative position divergence, and warning noise. **Fix
  direction** ("wire owns the lifetime"): broadcast `netSyncPropSpawn` at the
  `objSetDropped` chokepoint for synced chr-held weapons entering the world, and
  suppress the client's local corpse-drop so the wire copy is THE gun. Touches the
  ghost-gun/double-spawn lifecycle family (`PORT_NET_PROP_LIFECYCLE.md`) — needs its
  own pass + soak run. Deferred.
- High bandwidth usage, especially with 8 players; recommend `Net.Server.UpdateFrames=2`.
- **16-player hard ceiling: the `obj->hidden` attacker/owner field is 4 bits — exactly full at `MAX_PLAYERS` 16.** Kill attribution and object ownership pack the playernum into bits 28-31 of `obj->hidden` (read as `(obj->hidden & 0xf0000000) >> 28` at e.g. propobj.c:4257/4535/11663, written at propobj.c:15047 `obj->hidden |= (playernum << 28) & 0xf0000000`). 4 bits holds 0-15 exactly, so the current `MAX_PLAYERS` 16 is the hard ceiling: any future `MAX_PLAYERS > 16` would **silently truncate** attacker/owner playernums (wrong kill credit; mis-attributed mine / autogun / dropped-weapon ownership) with **no compile error**. The autogun owner already ships as a full client-id byte on the wire, but this *local* packing is still 4-bit. Before widening past 16, either widen the field (find a free `hidden`/`hidden2` bit range) or add a `MAX_PLAYERS <= 16` static guard so it can't be tripped silently. (Noted only in the proto-75 widening commit until now.)
- **Scoreboard / lobby-menu row layouts clip beyond 8 players in 9-16-player games (cosmetic).** The `MAX_PLAYERS` 8→16 widening grew the *data* arrays (all `MAX_*`-sized — confirmed by the 2026-06-16 stranded-combatant-array audit) but not the fixed UI row layouts, so a full 9-16-player roster's scoreboard / teams rows can render past the visible area. **Cosmetic only — no OOB.** Deferred follow-up from the proto-75 commit.
- Sim bots are position-driven on clients — `SVC_CHR_FIRE` syncs shoot sound + muzzle-flash on/off, and the chr-state block in `SVC_PROP_MOVE` syncs body rotation and animation. `chr->actiontype` is **not** synced (would crash; see Sim Position Sync section); the client always dispatches sim chrTick as `ACT_STAND`, so visible animation comes only from the synced `animnum` and not from any per-action tick logic. Aim/look direction (head/torso) and partial-body animations (limb-specific layers) are still server-authoritative only.
- Punching and a few weapon-animation sounds still play first-person for every listener — the punch swing/hit goes through a code path outside the GUNCMD_PLAYSOUND hook we patched. Source TBD.
- Lag-comp is broad-phase (sphere) only. Narrow-phase bone matrix rewind was attempted and reverted after crashing the host — see Lag Compensation section. A safer narrow-phase pass needs to re-derive matrices on demand instead of writing into the per-frame `gfxAllocate` buffer.
- CSP is back to the simpler retarget-only behavior. At very high ping the local player may drift slightly behind the authoritative position when constantly diverging from the server, but it's stable — no exponential teleporting. Snap branch now uses `chrSetPos` (re-derives ground/rooms + resets `player->vv_manground`/`vv_ground`/`vv_theta`) so snaps actually stick — fixes the previous "client thinks it's standing, server says it's fallen, ack/snap loop forever" desync.
- Pitch-shift effects on remote players' weapon sounds (e.g., mauler charge) are skipped because `psCreate` returns a channel index, not a `struct sndstate *` handle. Local player still gets the effect via `sndStart`.
- Weapon equip / pickup sounds (the ~30 other `sndStart` sites in `bondgun.c`) are still non-positional for remote players. Less audible than fire sounds, so deferred.
- Host spectator mode: no pause-menu UI for per-panel mode/target selection — controls are gamepad-only (C-buttons + Z-trigger + sticks; see netplay CLAUDE.md). A pause-menu submenu is planned as a follow-up.
- Host spectator mode: audio listener still uses the engine's default (active panel via `setCurrentPlayerNum`), but no explicit "follow active panel" selector — 3D sound pan/volume may feel inconsistent when cycling panels rapidly.
- Host spectator mode: when the host's panel is in PLAYER/SIM mode and the target disappears mid-frame, the panel renders the last-known pose for one frame before failing over to freecam. Cosmetic only.
- Host spectator mode: not validated end-to-end (no build env in this workspace) — manual test plan in `~/.claude/plans/wanna-add-a-real-toasty-sketch.md`.
